# ZiadaPOS desktop release plan

## Review status

This is a local, review-only release preparation. No code has been pushed, no tag has been created, no GitHub Release has been published, and no release artifacts have been uploaded. The new workflow is intentionally not run from this workspace.

After the exact repository changes are reviewed and explicitly approved, pushing a `vMAJOR.MINOR.PATCH` tag will run `.github/workflows/desktop-release.yml`. That workflow builds on native Linux, Windows, and macOS runners, packages one desktop build per runner, and creates a GitHub Release. A tag containing a prerelease suffix (for example `v0.2.0-rc.1`) is marked as a prerelease. The workflow validates the tag and sets the Wails app version from it.

The existing `.github/workflows/desktop-build.yml` remains a manual build/test workflow that uploads short-lived Actions artifacts only; it does not publish a release.

## Release payload produced by the workflow

For a tag such as `v0.2.0`, the workflow attaches:

| Release asset | Contents |
|---|---|
| `ziadapos-0.2.0-linux-amd64.tar.gz` | Linux x86-64 `ZiadaPOS` executable |
| `ziadapos-0.2.0-windows-amd64.zip` | Windows x86-64 `ZiadaPOS.exe` |
| `ziadapos-0.2.0-macos-native.zip` | `ZiadaPOS.app` built for the native macOS hosted runner architecture |
| `INSTALLATION.md` | Runtime requirements and first-run notes from `apps/desktop/RELEASE.md` |
| `SHA256SUMS` | SHA-256 checksums for the preceding release assets |

GitHub may also provide its standard source archives for the release tag. This is a first distribution slice, not an installer/update system. macOS is one native runner architecture, not a universal binary; the Windows and Linux jobs target amd64.

## App icons

The shared tracked source is [`apps/desktop/build/appicon.png`](../apps/desktop/build/appicon.png), converted from the existing square `apps/web/public/ziada-final.jpeg` logo. Wails v2 uses it to generate a Windows `.ico` resource in the executable and `iconfile.icns` in the macOS `.app` bundle; the Linux Wails window receives the PNG through `options.Linux.Icon`. The release workflow checks that the Windows and macOS icon outputs exist before packaging. The Linux test checks that the embedded PNG is valid.

This follows the [Wails v2.15 manual-build and asset-generation guidance](https://wails.io/docs/guides/manual-builds/); the macOS app-bundle resource is generated by Wails' native macOS packaging stage.

These deliverables are archives, **not installers**. The Linux archive does not create a `.desktop` entry or register an application-menu/launcher icon; it only contains the executable, whose running Wails window uses the ZiadaPOS icon. The Windows ZIP contains an `.exe`, and the macOS ZIP contains the `.app` bundle with its icon.

## Runtime and distribution limitations

- The Go API, PostgreSQL, Redis, and object storage are **not** bundled. The app needs access to the existing API. `POS_API_URL` defaults to `http://localhost:8080/api/v1` and can be set before launch.
- Linux needs GTK 3 and WebKit2GTK 4.1 at runtime.
- Windows needs the WebView2 Runtime available on the computer.
- macOS uses the system WKWebView.
- These builds are not code-signed or notarized and are not packaged as native installers. Windows WebView2 bootstrap, macOS signing/notarization, Linux installer formats, automatic updates, and rollback are not included.
- The packaged app's `--browser` mode serves its UI only on loopback at a random local port; it is not a hosted public web release or offline POS implementation.

Treat these artifacts as initial testing builds until signing, installation, update, and per-platform smoke-test requirements are addressed.

## Browser-mode evidence

[`screenshots/browser-mode-sign-in.png`](screenshots/browser-mode-sign-in.png) is the requested screenshot from the already-built app launched with `--browser`. It shows the unauthenticated sign-in page on the local loopback URL. The screenshot surfaced a public-image access issue; the review payload includes a minimal route-guard fix so public image assets are not redirected to sign-in.

## Verification boundaries

- The desktop Go tests and Linux browser-mode loopback smoke test are run locally before handoff.
- Windows and macOS builds can only be verified by running the new workflow on their native GitHub Actions runners.
- The workflow itself, tag creation, repository push, GitHub Release creation, and release asset upload remain unperformed pending review and explicit confirmation.
